# 翼枢分流应用设计方案

## 一、建设目标

开发一个正式的 Windows 分流应用，在不改变翼枢自身业务逻辑的前提下，将翼枢 WireGuard 隧道从全局路由收窄为授权资源路由。

应用由 Windows 后台服务和托盘程序组成：后台服务负责持续维护分流，托盘程序负责展示状态和接受用户操作。除非后台服务被停止，或者用户明确选择“关闭分流”，否则系统始终保持“期望启用分流”的状态。

本应用只管理路由和 WireGuard `AllowedIPs`，不读取、不写入、不切换 hosts，也不设置或替换 Windows DNS。

## 二、总体架构

### 2.1 后台服务

后台服务以 `LocalSystem` 身份运行，设置为开机自动启动，是路由状态的唯一管理者，负责：

- 检查翼枢进程、`wg.exe`、`misas` 接口和 WireGuard peer。
- 读取并校验分流配置。
- 修改 WireGuard peer 的 `AllowedIPs`。
- 使用 Windows IP Helper API 创建、查询和删除活动路由。
- 周期性执行健康检查，并在翼枢恢复后重新应用分流。
- 保存事务快照、运行状态和诊断日志。

服务不启动翼枢界面，也不在 Session 0 中模拟用户操作。

### 2.2 托盘程序

托盘程序使用 .NET 10 WinForms `NotifyIcon` 实现，不创建主窗口，不使用 XAML。托盘以普通用户权限运行，通过仅限本机访问的命名管道与后台服务通信。

托盘退出只关闭托盘界面，不关闭后台服务，也不改变当前分流状态。只有选择“关闭分流”才会改变服务的期望状态。

### 2.3 系统能力的使用

- 路由查询和修改使用 Windows IP Helper API，包括 `GetIpForwardTable2`、`CreateIpForwardEntry2` 和 `DeleteIpForwardEntry2`。
- 网卡和接口索引从 Windows 网络接口信息中取得，不硬编码接口索引、默认网关或本地网卡名称。
- WireGuard 状态读取和 peer 修改使用翼枢自带的 `resources\wg.exe`。
- 不直接修改 `misas.conf`，不调用自制网络驱动，不实现新的隧道协议。

## 三、状态模型

应用将“用户期望”和“实际运行状态”分开保存，避免把等待或故障错误显示为已启用。

实际状态包括：

- `已关闭`：用户明确关闭分流。
- `等待翼枢`：用户期望启用，但翼枢进程、隧道或 peer 尚不可用。
- `正在启用`：正在执行启用事务。
- `已启用`：目标 `AllowedIPs` 和 Windows 路由均已核验。
- `正在关闭`：正在执行关闭事务。
- `故障`：事务失败，或者无法确认系统实际状态。

首次安装默认期望状态为启用。用户通过托盘关闭后，关闭状态需要持久化；服务或系统重启后仍保持关闭，直到用户再次选择“启用分流”。

## 四、健康检查和自动恢复

服务周期性检查以下组件：

- 后台服务自身状态。
- 翼枢进程是否运行。
- `resources\wg.exe` 是否存在且可执行。
- `misas` IPv4 接口是否存在。
- WireGuard peer 是否可读取。
- 当前 `AllowedIPs` 是否与有效配置一致。
- 服务记录的目标路由是否存在于正确接口。

期望启用但翼枢不可用时，状态显示为“等待翼枢”，而不是“已启用”或“已关闭”。翼枢重新可用后，服务自动执行完整启用事务。

建议采用 2 秒、5 秒、10 秒、30 秒的退避重试间隔；恢复正常后回到常规心跳周期。这样既能及时恢复，也能避免故障期间反复刷日志。

如果已启用状态下翼枢退出、隧道消失或 peer 被重建，服务清理已经失效的本地状态并转入“等待翼枢”。隧道恢复后重新建立事务快照并应用分流。

## 五、事务设计

### 5.1 启用事务

启用分流按以下顺序执行：

1. 完整读取并校验配置，计算去重后的目标 CIDR。
2. 验证翼枢进程、`wg.exe`、`misas` 接口和 WireGuard peer。
3. 原子保存 peer 公钥、原始 `AllowedIPs`、接口索引、原始路由和本次将创建的路由。
4. 在 `misas` 接口创建目标活动路由。
5. 使用 `wg.exe set` 将 peer 的 `AllowedIPs` 收窄到目标 CIDR。
6. 删除仅由原始宽泛 `AllowedIPs` 产生、且不属于目标集合的隧道路由。
7. 重新读取 WireGuard 和 Windows 路由表，确认结果一致后提交事务。

任何步骤失败都使用事务快照恢复原始 `AllowedIPs` 和路由；恢复结果也必须核验。无法完成回滚时进入“故障”状态并保留快照，不得错误显示为已关闭。

### 5.2 关闭事务

关闭分流按以下顺序执行：

1. 将持久化的用户期望立即设置为关闭，停止自动启用和重试。
2. 读取并校验最近一次成功事务的快照。
3. 如果隧道仍存在，恢复原始 `AllowedIPs`。
4. 删除本应用创建的路由，并恢复事务中记录的原始路由。
5. 核验 WireGuard 和路由状态，成功后删除活动事务快照。

如果翼枢接口已经消失，对应活动路由也已经随接口消失，服务可以清理快照并判定关闭完成。如果接口仍存在但恢复失败，则进入“故障”状态并继续保留恢复数据。

停止 Windows 服务时同样执行关闭事务。托盘退出不触发关闭事务。

## 六、托盘菜单

托盘右键菜单至少包含：

- `分流状态：已启用／等待翼枢／已关闭／故障`
- `启用分流`
- `关闭分流`
- `组件状态`
  - 后台服务
  - 翼枢进程
  - `wg.exe`
  - `misas` 接口
  - WireGuard peer
  - 路由配置
  - 最近一次心跳时间
  - 最近一次错误
- `重新加载配置`
- `打开配置目录`
- `查看日志`
- `退出托盘`

启用、关闭和重新加载期间，需要暂时禁用可能冲突的菜单项。所有耗时操作异步执行，不能阻塞托盘消息循环。

配置只允许在已关闭状态重新加载。推荐操作顺序为：关闭分流、编辑配置、重新加载配置、启用分流。

## 七、路由配置

运行配置只保留实际需要的参数和 CIDR，不再保存导入时间、日志来源、资源名称、端口或重复前缀。

建议配置格式如下：

```json
{
  "version": 1,
  "yiShu": {
    "directory": "C:\\Program Files\\YiShu",
    "interface": "misas",
    "processName": "翼枢"
  },
  "routing": {
    "minimumPrefixLength": 8,
    "infrastructurePrefixes": [
      "1.2.3.4/32",
      "172.28.160.193/32"
    ],
    "resourcePrefixes": [
      "172.27.103.0/24",
      "172.28.72.0/24",
      "172.29.16.0/24"
    ]
  }
}
```

配置加载时需要执行以下校验：

- 只接受合法 IPv4 CIDR。
- 对 CIDR 进行规范化、排序和去重。
- 拒绝宽于 `minimumPrefixLength` 的路由。
- 不允许空的基础设施或资源前缀被静默忽略。
- 配置错误时保留当前已确认状态，不应用部分配置。

### 7.1 基础设施路由

- `1.2.3.4/32` 是翼枢控制面地址。收窄全局路由后仍需确保它通过翼枢隧道可达，避免翼枢反复执行网络修复。
- `172.28.160.193/32` 是翼枢写入 `misas` 网卡的 DNS 服务器地址。当前系统显示 `misas` DNS 包含 `198.18.0.1` 和 `172.28.160.193`。保留该精确路由是为了维持翼枢现有网卡配置的完整性，并不表示本应用负责设置或管理 DNS。

### 7.2 资源路由

- `172.27.103.53` 已包含在 `172.27.103.0/24` 中，无须重复配置 `/32`。
- `172.29.16.6` 和 `172.29.16.2` 已包含在 `172.29.16.0/24` 中，无须重复配置 `/32`。
- `172.28.158.211` 至 `172.28.158.215` 不再纳入翼枢分流。

## 八、DNS 与 hosts 的边界

本应用不管理 DNS 和 hosts。域名最终解析到哪个 IP，由本地网关 DNS、Windows DNS 配置或用户自行维护的 hosts profile 决定；本应用只根据解析后的目标 IP 选择是否通过翼枢。

本地网关 DNS 可以解析的 `srdcloud.cn` 系列不需要任何 hosts 记录。它们解析到本地网络地址后，不命中翼枢资源路由，因此直接走本地网络。

用户只需自行保留一份“翼枢专用资源” hosts profile：

```hosts
# 翼枢专用资源
172.27.103.53 snc-cluster.ipsdn.com
172.29.16.6 testnacos.cn
```

这里的 hosts 只负责名称解析：

- `snc-cluster.ipsdn.com` 解析到 `172.27.103.53` 后，命中 `172.27.103.0/24`，通过翼枢访问。
- `testnacos.cn` 解析到 `172.29.16.6` 后，命中 `172.29.16.0/24`，通过翼枢访问。

正式应用不会读取或修改上述 profile。安装迁移时应删除旧工具曾写入 Windows hosts 的托管区块，此后不再触碰 hosts 文件。

## 九、部署与迁移

- 使用 .NET 10 开发，发布为 `win-x64` 自包含程序。
- 后台服务设置为自动启动；托盘程序在用户登录后启动，但服务不依赖托盘存在。
- 程序、配置、状态和日志放在独立目录中，不混入翼枢安装目录的业务文件。
- 安装时先安全停止现有 `YiShuSplit` PowerShell 服务并等待其恢复旧分流。
- 备份现有 JSON、状态和日志，再迁移为精简配置。
- 删除旧服务注册，避免新旧管理器同时修改 `AllowedIPs` 和路由。
- 清除旧 hosts 托管区块，但保留原始 hosts 备份供人工恢复。

## 十、验收标准

- 系统启动且翼枢尚未连接时，服务显示“等待翼枢”，不显示虚假的已启用状态。
- 翼枢连接后，服务自动完成启用事务并显示“已启用”。
- 只有配置中的 CIDR 进入 `misas`，本机、公网和本地优先资源保持原路由。
- `snc-cluster.ipsdn.com` 和 `testnacos.cn` 通过本机 hosts 解析后走翼枢。
- `srdcloud.cn` 系列由本地网关 DNS 解析并走本地网络。
- 翼枢断开后状态转为“等待翼枢”，重新连接后自动恢复分流。
- 用户关闭分流或停止服务后，原始 `AllowedIPs` 和路由得到恢复。
- 任一事务失败时有明确故障状态、组件状态和日志，不出现“部分成功但显示已启用或已关闭”的情况。
- 托盘退出不影响后台分流；服务停止才会执行关闭事务。
